From emergency patch to modern platform: securing a legacy PHP estate without a big-bang rewrite

A US specialty insurer ran its agent portal, quoting tools and dozens of marketing sites on PHP, some of it years out of support. When an actively exploited PHP flaw landed, nobody could say quickly where PHP was running. The goal was to close that exposure in days, then turn a one-off scramble into a platform that stays patched.

The situation

A specialty insurer in the United States had grown its digital estate over fifteen years. The agent portal and quoting tools ran on PHP, alongside dozens of marketing and campaign sites built by agencies, a document-generation service, and vendor appliances that embedded PHP without anyone realising. Some runtimes were current; others were several releases out of support.

Why now. On 26 October 2026, CISA added two PHP remote code execution flaws, known as PHP2Shell, to its Known Exploited Vulnerabilities catalog and gave US federal agencies days to remediate13. Researchers reported successful exploitation in the wild2. For a regulated insurer, the first question from the board was simple: are we exposed? The honest answer was "we don't know yet", and that was the real problem to solve.

What had to be true

  • Exposure closed within days: every affected runtime patched to a fixed release or isolated.
  • One trustworthy inventory of PHP runtimes, versions and owners, refreshed automatically.
  • No outage for agents during quoting hours.
  • Visibility before change: know what each legacy app actually does in production before touching it.
  • A durable fix, so the next advisory is routine work, not a crisis.

Architecture

The data flow, end to end

The patched releases (8.5.12, 8.4.27, 8.3.36 and 8.2.35) were available from 21 October2. Anything on PHP 8.1 or older could not simply be patched, because those branches no longer receive security fixes4; CISA's advice for such systems was to take them offline until they could be upgraded1.

The hard part: changing systems nobody fully understood

The quoting tool had no tests and few people who knew it well. Before upgrading or migrating anything, the team added request tracing at the web server. The OpenTelemetry module for Apache HTTP Server records each incoming request as a trace, with spans for the modules involved, so you can see what the server is doing without changing application code5.

A few weeks of traces showed which routes agents actually used, which were dead, and which called downstream systems. That turned an unknown monolith into a ranked list of routes to move.

The first deliverable of any legacy modernisation is a map of what the system really does in production. Traces give you that map for free.

With that map, quoting functions moved behind a routing facade one route at a time, the strangler fig approach6: new services took over a route, traffic shifted gradually, and the old code path was removed once unused. More on the observability side in OpenTelemetry Collector deployment patterns.

How it ran

Key decisions and trade-offs

What I'd do again, and differently

Again: inventory first, then golden images, then tracing before touching code. Differently: put patch SLAs and the exceptions register in place before an emergency, not after. The scramble was mostly the cost of not knowing what was running. For the incident-review side, see running useful postmortems, and for the week's context, tech news for 29 October.

FAQ

Common questions

How do you find every PHP runtime in a large estate?

Combine sources: cloud and hypervisor inventories, container image scans, web server banners from external and internal scans, package manager data on hosts, and DNS records for forgotten sites. Reconcile them into one list with an owner per runtime, and refresh it automatically.

Is a web application firewall enough for an exploited PHP flaw?

No. A WAF rule can buy time while you patch, but it is a compensating control. The fix is upgrading to a patched release, or isolating anything that cannot be upgraded, as CISA advises for PHP 8.1 and older.

Why not rewrite the legacy PHP applications?

Big-bang rewrites of business-critical systems are slow and risky. The strangler fig approach puts a facade in front of the old system and replaces it route by route, so each step is small, testable and reversible.
