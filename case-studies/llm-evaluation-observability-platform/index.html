Shipping AI features with evidence: a shared evaluation and observability platform

Several product teams had shipped AI features, each with its own prompts, its own vendor calls and its own idea of 'good'. Model upgrades were risky, regressions were found by customers, and nobody could say what an AI feature cost to run. The goal was one platform for evaluating, releasing and observing every LLM feature.

The situation

A software company had moved quickly on AI. Support had an answer assistant, sales had an email drafter, the core product had a summariser and a natural-language search box. Each team had picked prompts, vendors and settings independently. When a model provider released a new version, nobody knew which features would get better and which would quietly break. Quality problems surfaced as customer tickets. Finance saw one large model invoice and could not split it by feature.

Leadership did not want to slow the teams down. They wanted the same confidence in AI releases that they already had in ordinary code releases.

What had to be true

  • Every AI feature has an evaluation set that reflects real use, owned by the team that ships it.
  • Changes ship through gates: a prompt, model or retrieval change runs the evals before it reaches customers.
  • Every model and tool call is traceable, with latency, tokens and errors, using an open standard rather than a vendor format.
  • Sensitive content is not logged by default.
  • Cost and quality are visible per feature, so product managers can make trade-offs.

Architecture

The data flow, end to end

Tracing followed the OpenTelemetry semantic conventions for generative AI, which standardise how model calls are recorded, including the model, input and output token counts and, when explicitly enabled, prompt and completion content12. Standard metrics for token usage and operation duration made cost and latency comparable across features and vendors3. The detail is in LLM observability with OpenTelemetry.

The hard part: evaluation sets that predict production

Building the pipeline was straightforward. Building evaluation sets that actually predicted how features behaved for customers was not. Generic benchmarks said little about whether the support assistant would answer a specific customer's question correctly.

  • Cases drawn from real, anonymised usage, grouped by intent, with a slice of known hard and sensitive cases.
  • Deterministic checks wherever possible: format, required fields, citations present, forbidden content absent.
  • Rubric-based model graders only where judgement was needed, calibrated against human labels. Research on LLM-as-a-judge found strong models can match human preference agreement, but also documented position and verbosity biases that need controlling4.
  • Regular refresh from production misses, so the set evolves with the product.

More on this in evaluation sets that predict production and, for agentic features, evaluating AI agents.

An eval set is a product artefact, not a test fixture. The team that owns the feature owns its definition of good.

How it ran

Key decisions and trade-offs

The programme was mapped to the NIST Generative AI Profile, which gave the risk team a recognised structure for issues such as confabulation, information security and data privacy5.

What I'd do again, and differently

Again: start with tracing and cost per feature, because visibility creates demand for evaluation. Differently: write a model upgrade playbook in the first phase. Provider version changes arrive on their schedule, not yours, and a rehearsed path from new model to gated rollout takes the drama out of them.

FAQ

Common questions

What should an LLM evaluation set contain?

Real examples of what users ask, with known good answers or clear grading criteria, covering common cases, known failure modes and sensitive edge cases. It should be owned by the feature team and refreshed from production feedback.

Can LLMs grade other LLMs reliably?

Research on LLM-as-a-judge found strong models can agree with human preferences at a level comparable to agreement between humans, but also documented biases such as position and verbosity bias. Use judges with calibration against human labels, not as the only signal.

Does tracing LLM calls capture prompts and user data?

Not by default in the OpenTelemetry GenAI conventions: content capture is opt-in because prompts and tool arguments can contain sensitive data. Metadata such as model, token counts and durations is captured without content.
