Building a fintech platform for UAE Open Finance: consent, security and a single hub

A UAE fintech had built its product on screen scraping and one-off bank integrations. The Central Bank's Open Finance framework offered a regulated, standardised alternative through a central API hub. The goal was to re-platform around consent and secure APIs without stalling the product roadmap.

The situation

A fintech serving customers in the UAE offered budgeting and cash-flow insights built on account data. Getting that data had meant a patchwork: screen scraping for some banks, bilateral integrations with others, and manual statement uploads as a fallback. Each connection broke differently, security reviews were difficult to pass, and the approach had no future as regulation matured.

The Central Bank of the UAE's Open Finance Regulation changed the picture by establishing a regulated framework for open finance services1. The question for leadership was how to move onto it cleanly, while continuing to ship features.

What had to be true

  • One integration path through the regulated framework, replacing scraping and bespoke connectors.
  • Consent as a product feature: customers see what they shared, with whom, for how long, and can revoke it.
  • Financial-grade security that a bank's or regulator's reviewer would recognise.
  • Data minimisation: store only what each feature needs, for as long as it needs it.
  • Clear regulatory boundaries, including where free zone permissions do and do not apply.

The framework is described as having three parts: a trust framework, an API hub and common infrastructure services2. Commentary highlights that the API hub is operated by a Central Bank subsidiary, Nebras, as a single gateway between providers and licensed institutions, that participation is mandatory for licensees in respect of in-scope products, and that DFSA or FSRA permissions in the financial free zones do not by themselves grant access to the onshore hub3.

The hard part: security that reviewers recognise

Financial APIs attract determined attackers, and generic OAuth setups leave room for token theft and replay. The OpenID Foundation's FAPI 2.0 security profile defines a hardened profile of OAuth 2.0 and OpenID Connect for exactly these APIs; its security profile and attacker model were approved as final specifications, and conformance tests and certification are available45. Building to a recognised profile meant security discussions with partners started from a shared baseline rather than a custom design.

  • Sender-constrained tokens and strong client authentication, so a stolen token alone is not enough.
  • Keys held in a key management service or hardware security module, never in application configuration.
  • Conformance testing in CI against the profile, run before every release of the connector.
  • Product services given no direct access to tokens or the hub; they consume events and minimised data.

In open finance, consent is not a checkbox. It is the primary key of the whole data model: every token, fetch and stored field should trace back to one.

What I'd do again, and differently

Again: treat consent as the centre of the data model and build to a recognised security profile from the start. Differently: settle the licensing and regulatory perimeter before detailed design, especially the onshore and free zone question. FAQ

Common questions

What is the UAE Open Finance framework?

A Central Bank of the UAE regulation that sets up open finance through a trust framework, a central API hub and common infrastructure services, so licensed institutions and third-party providers exchange data and initiate services through standardised, consented APIs.

Do fintechs connect to each bank separately?

Commentary on the framework highlights its centralised API hub, operated by a Central Bank subsidiary, as a single gateway between third-party providers and licensed institutions, rather than separate bilateral integrations.

What is FAPI 2.0?

A financial-grade API security profile for OAuth 2.0 and OpenID Connect from the OpenID Foundation. Its security profile and attacker model were approved as final specifications in February 2025, with conformance tests and certification available.
