Automating lease, ID and invoice intake without letting a model write to the ledger

Leases, identity documents and supplier invoices arrived as scans, photos and PDFs, and every one was keyed in by hand before a tenant could be onboarded or a bill paid. The goal was to automate the routine documents and make the rest faster to check, while keeping the core system's data trustworthy.

The situation

A property operator onboarded tenants and paid suppliers through a core property management system. Everything that fed it arrived as documents: signed leases, identity documents, proof of address, supplier invoices and service contracts. Each was opened, read and keyed by hand. Onboarding waited on the queue, keying errors surfaced later as billing disputes, and the team spent its time transcribing rather than checking.

Earlier attempts with template-based OCR had struggled because the documents varied too much: different lease templates, scanned and photographed IDs, and invoices in every layout a supplier could invent.

What had to be true

  • Every value validated before it reaches the core system, by rules the business can read.
  • The model never writes: it proposes a record, and deterministic code decides what is posted.
  • Uncertain documents go to people, with the reason and the source region visible.
  • Personal data handled deliberately: limited access, defined retention and no identity documents in logs or prompts beyond what extraction needs.
  • Traceability from any posted value back to the page it came from.

Architecture

Each document type had a versioned JSON Schema describing its fields, types, formats and required properties1. The model was asked to return output conforming to that schema, and the same schema validated the response, so a malformed answer failed loudly instead of slipping through. More on the pattern in structured outputs for reliable LLM integration.

The data flow, end to end

The audit and staging tables in Postgres carried their own check, not-null and foreign key constraints, so invalid states were rejected by the database as well as by the application3. Retries were safe because posting was idempotent, the same discipline described in idempotent payment and order pipelines.

The hard part: confidence you can act on

Extraction quality was rarely the blocker. Deciding when to trust it was. A model's own statement of certainty is not a reliable signal, so confidence was built from evidence instead:

  • Arithmetic and consistency checks: invoice lines must sum to totals, lease dates must be in order, rent schedules must match the term.
  • Reference checks: the unit, tenant or supplier must exist and match what the document claims.
  • Field-level thresholds set per document type from a labelled sample, with stricter rules on fields that move money or identify people.
  • Reason codes on every exception, so the team could see which rule or field caused most reviews and fix the cause.

Documents are also untrusted input. Text inside an uploaded file can carry instructions aimed at the model, a form of indirect prompt injection2. The defence was architectural: the extraction model had no tools and no credentials, its output was confined to the schema, and posting was done by code that ignored anything outside defined fields. See prompt injection defence.

The model is the least trusted component in the pipeline. Design so that the worst it can do is produce a record that fails validation.

How the engagement ran

Ongoing monitoring of exception rates, corrections and drift by document type followed the measure-and-manage approach of the NIST AI Risk Management Framework4.

What I'd do again, and differently

Again: keep the model away from credentials and let validation, not the model, decide what is posted. Differently: build the labelled sample before the pipeline. Every threshold discussion went faster once there was a shared set of real documents to measure against.

FAQ

Common questions

Can an LLM extract data from leases and invoices reliably?

It can extract most fields well, but reliability comes from what surrounds the model: a strict output schema, deterministic validation, cross-checks against known data and a review queue for anything uncertain.

Should the model post directly to the core system?

No. The model should only produce a candidate record. Deterministic code validates it and posts it, so the model never holds credentials or decides what is written.

How do you set confidence thresholds?

Measure against a labelled sample of real documents, per document type and per field, and set thresholds from observed error rates rather than the model's self-reported certainty.
