Case study · Retail streaming

Replacing nightly stock syncs with a live inventory stream

Stock moved all day in stores, warehouses and online, but channels learned about it once a night. Overselling was the predictable result. The goal was to stream every committed stock and order change from the operational databases into projections that every channel could read in near real time.

The situation

A retailer sold through physical stores, its own website and several marketplaces. Stock levels lived in a warehouse system and store systems, orders in an order management database, and each channel received a stock file once a night. During the day, the same last unit could be sold in a store, online and on a marketplace before anyone knew.

The workarounds made things worse: large safety buffers that hid sellable stock, manual cancellations, and ad hoc point-to-point integrations that each team had built to get fresher data for its own channel.

What had to be true

  • Every committed change is captured, without polling or adding load to operational databases.
  • No dual writes: an order and its event either both happen or neither does.
  • Channels read a projection, not the source systems.
  • History is replayable, so a bug in a projection can be fixed and rebuilt.
  • Contracts are explicit, so source teams can change their schemas without breaking consumers.

Architecture

Log-based change data capture reads committed row-level changes from the database's transaction log, so applications consume changes rather than querying the source1. That became the backbone, with a stream processing layer building inventory views for each consumer.

The data flow, end to end

More on the capture side in change data capture and event streams, and on duplicate-safe consumers in idempotent order pipelines.

The hard part: events that mean something

Streaming raw table changes was quick to demonstrate and the wrong long-term contract. Consumers ended up decoding internal columns and status codes, and any schema change in the source broke them. The transactional outbox pattern addresses this: the service writes a domain event to an outbox table in the same transaction as the business change, and a relay publishes it3. Debezium's outbox event router does that relay from the log, routing events to topics by aggregate type and keying them by aggregate identifier2.

  • Events were designed with the consuming teams: "stock adjusted", "order allocated", "reservation released", not "row updated".
  • Keys were chosen for ordering: everything about one SKU at one location lands in one partition, in order.
  • Contracts went into the schema registry with compatibility rules, following a data contracts approach.

For current state, compacted topics keep the latest record per key and support rebuilding state after a failure4, which let new projections bootstrap without a bulk extract from the source.

CDC moves data quickly; it does not decide what the data means. Design the events with the teams who will read them.

How it ran

Operationally, the signals that mattered were connector health, consumer lag per projection and the reconciliation drift report. Those went on one dashboard owned by the platform team, with alerts tied to what a channel would notice (stale stock) rather than to every broker metric. Traces carried the event identifier from commit to read model, so a disputed stock figure could be followed back to the change that produced it.

What I'd do again, and differently

Again: a thin slice end to end before scaling, shadow running against the old feed, and reconciliation from the start. Differently: agree the reservation and allocation rules with operations earlier. Live data exposed business rules that had never been written down, and those took longer to settle than the streaming platform.

FAQ

Common questions

What is change data capture?

Change data capture reads committed changes from a database's transaction log and publishes them as events, so other systems can react without polling or nightly extracts.

Should you stream raw table changes or domain events?

Raw table changes are quick to start but couple consumers to the source schema. The transactional outbox pattern publishes deliberate domain events in the same transaction as the change, which is safer as the number of consumers grows.

Does real-time inventory remove overselling entirely?

No. It narrows the window in which channels act on stale stock. Reservations, safety buffers and clear rules for concurrent orders are still needed.
