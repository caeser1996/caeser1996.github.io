One login bug away: hardening single sign-on, staff access and integration keys for a UK B2B SaaS company

A UK software company sold a collaboration platform to enterprises, most of whom signed in through their own identity providers. Its engineers had built single sign-on support over years, one customer request at a time. Staff could open customer workspaces for support, and integrations held keys to code hosting and the CDN. When another SaaS company disclosed that a flaw in its SSO flow let an attacker pose as staff and reach production, the board asked whether the same chain existed here.

The situation

A UK software company sold a collaboration and documentation platform to mid-sized and large organisations. Most enterprise customers signed in through their own identity providers using SAML or OIDC, and the company had added support for each provider's quirks over several years, in more than one part of the codebase. Support engineers could open any customer workspace to troubleshoot, using the same login system as customers with an internal flag. Integrations with code hosting, the CDN and DNS used long-lived keys, some readable from internal tools staff could reach.

Why now. In November 2026, GitBook disclosed that an attacker used a flaw in its SSO login flow to create sessions as staff, then reached a misconfigured code-hosting integration, internal repositories and a CDN API key that gave production access12. The same week, Apify confirmed that sign-in tokens and two-factor recovery codes had been accessed in an attack3. The UK's voluntary Software Security Code of Practice, published by the government and NCSC, sets expectations for vendors on secure development and on telling customers about incidents45, and enterprise customers had begun asking about it in security reviews.

What had to be true

  • One way in: a single, well-tested authentication path for all SSO, not several.
  • Staff are different: staff access never shares the customer login path.
  • No standing access: support access is granted per case, time-limited and logged.
  • No chains: a staff session cannot reach keys that reach production.
  • Visible: unusual sessions and token use raise alerts.
  • Explainable: if something happens, customers are told quickly what to rotate.

Architecture

All SSO handling moved into one authentication service built on maintained SAML and OIDC libraries, configured strictly: signatures required on assertions, audience and recipient checked, replay prevented and clock skew limited. Provider-specific workarounds became configuration in one place rather than code scattered across the product. Staff signed in through a separate identity provider with hardware security keys; a customer's SSO configuration could never create a staff session.

The data flow, end to end

The hard part: breaking the chain from login to production

Assume the login will be bypassed one day. SSO protocols are intricate and implementation bugs recur across the industry. The design question was therefore not only "is our SSO correct?" but "what can an attacker do with a forged session?". For customer sessions, the answer became: one tenant's data, nothing else. For staff sessions, it became: nothing, until access to a specific workspace is approved, and never the integration keys. The model borrowed from how Kubernetes treats every API request: authenticate, authorise, then apply policy before anything is allowed6.

Integrations with too much reach. The code-hosting integration had been installed with broad permissions years earlier, and CDN and DNS keys could change production routing. Each integration was reinstalled with the minimum permissions it needed, CDN and DNS changes moved to the deployment pipeline with short-lived tokens, and the secrets manager stopped allowing humans to read production secrets at all; only workloads could.

Rotation customers can actually do. GitBook's response asked customers to create new API tokens, rotate integration secrets and review recent changes made by its app1. The company wrote its own version of that notice in advance, listing exactly what customers would need to rotate, and built a one-click way for administrators to revoke all tokens for their workspace.

Every SaaS login flow will have a bug one day. What matters is that a forged session leads nowhere valuable: one tenant at most, never the staff console, never the keys.

What I'd do again, and differently

Again: separate staff access first; it removed the worst-case chain within weeks. Differently: commission an external test of the SSO implementation earlier; it found edge cases in provider-specific handling that internal reviews had missed. FAQ

Common questions

Why is a SaaS company's SSO flow a high-value target?

Because a flaw there can let an attacker create sessions as any user, including staff with broad access. If staff sessions can reach integrations and keys, one login bug can lead to production, as GitBook's November 2026 incident showed.

How should support staff access customer accounts?

Through a separate staff identity with phishing-resistant MFA, using just-in-time access that is approved, time-limited, logged and, where customers require it, consented to, rather than standing access to every workspace.

What is the UK Software Security Code of Practice?

A voluntary code published by the UK government and NCSC in May 2025 setting baseline security principles for software vendors, including secure development, secure build environments and communicating with customers about incidents.
