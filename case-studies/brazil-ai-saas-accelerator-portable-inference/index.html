Not tied to one chip: accelerator-portable inference for a Brazilian AI software company

A Brazilian software company served its own fine-tuned language models to retail and banking customers from GPUs in a São Paulo cloud region. Its stack assumed one GPU family and one provider. New US licensing for advanced chips shipped to Brazil, and growing interest in cloud providers' own accelerators, made that assumption a business risk. The goal was inference that could move between accelerators and providers without a rewrite, and without data leaving Brazil.

The situation

A Brazilian software company sold AI features to retailers and banks: customer service assistants, document extraction and product search, built on open-weight models it had fine-tuned. It served them from GPUs rented in a São Paulo cloud region, because customers expected their data to stay in Brazil under the LGPD's rules on personal data5. Every part of the serving stack, from container images to the serving engine and capacity contracts, assumed one GPU family and one provider.

Why now. In November 2026 the US issued a rule requiring licences for exports of advanced AI chips to several countries, including Brazil, and tightening remote access to such chips12. At the same time, cloud providers were pushing their own accelerators harder; Amazon was reported to be near a deal for Decart, whose software helps models run on AWS's own chips3. For a company whose margins depended on inference cost, being tied to one chip in one region had become a business risk, not just a technical preference.

What had to be true

  • Models servable on more than one accelerator type, with evidence that quality held.
  • Applications unaware of the hardware: one interface, routing decided by the platform.
  • No accidental mismatches: images only scheduled where drivers and hardware fit.
  • Capacity from more than one provider, all inside Brazil.
  • Cost visible per model, per accelerator, so choices were made on numbers, not habit.

The hard part: the same model is not quite the same on different chips

Moving a model between accelerators sounds like a deployment detail. In practice the serving engine, numerical precision, kernels and memory limits differ, and small differences in outputs show up in exactly the places customers notice: extraction fields, tone, refusals. The team treated every accelerator build as a new release of the model, with the same evaluation set and acceptance thresholds as a retrain, before any production traffic moved.

The second trap was scheduling. An image built for one accelerator and its drivers must never land on a node that cannot run it. Node Feature Discovery reports hardware and system features of each node, and its image compatibility work lets an image declare requirements such as drivers and kernel features that can be validated against a node before scheduling4.

Portability is not free. Each additional accelerator adds a build, an evaluation run and an operational pool. The team supported two serving accelerator types plus CPU, and stopped there.

The gateway and routing approach follows LLM model routing and Kubernetes inference gateways; serving engine choices are covered in LLM inference serving, and capacity planning in the multi-region AI capacity case study.

What I'd do again, and differently

Again: put the gateway in first; it made every later step cheaper and gave the cost data that justified the rest. Differently: write evaluation sets for each product before starting, not during the first migration. The slowest part was agreeing what "good enough" meant for each customer-facing task. FAQ

Common questions

Why does chip licensing matter to a software company?

It changes how easily cloud and data centre providers in a country can obtain advanced accelerators, which affects price and availability of the capacity a software company rents.

Can the same model run on different accelerators?

Often yes, but not identically. Serving engines, numerical precision and kernels differ, so outputs, latency and cost must be checked per accelerator before moving production traffic.

How does Kubernetes help?

Node Feature Discovery reports hardware and driver features on each node, so images built for a given accelerator can be scheduled only where they are compatible, and a gateway can route traffic across pools.
