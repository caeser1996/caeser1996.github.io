Capacity you can move: multi-region AI serving for a US SaaS company when data centres stall

A US B2B software company had built AI features that customers now relied on daily. Its model serving sat in one cloud region with one provider, on capacity that was hard to expand. With demand for AI compute outrunning supply and voters pushing back on new data centres, the company needed AI capacity it could move, without rebuilding the product each time.

The situation

A US software company sold a workflow platform to mid-sized businesses. Over two years it added AI features: summarising records, drafting replies, extracting data from documents and an assistant inside the product. Customers adopted them quickly. The company served open-weight models on GPUs in one cloud region, with a managed model API for a few tasks. As usage grew, adding GPU capacity in that region became slow and uncertain, and latency spiked whenever demand peaked.

Why now. Demand for AI compute was running ahead of supply: Fortune reported Microsoft's CFO saying demand for its cloud still exceeded supply3. New capacity was arriving on long timelines and through complex financing, such as Google's credit backstop for Anthropic's Kentucky data centre lease4. And in the 3 November 2026 midterms, voters sided against data centres in 40 of 41 local ballot measures across 10 states, according to CNBC's analysis1, a sign of growing opposition to new AI infrastructure2. The board's question was simple: what happens to our AI features if we cannot get more capacity where we are?

What had to be true

  • No single point of capacity: AI features served from more than one region and provider.
  • Moving traffic is configuration, not a code change or a rebuild.
  • Customer data rules respected: some customers required US-only processing; some required specific providers.
  • Costs visible per feature and per customer, so capacity decisions follow value.
  • Quality held when traffic moves between models or providers.

The data flow, end to end

The hard part: moving traffic without changing behaviour

Routing is easy to draw and hard to trust. A summary from one model in one region should not read differently from a summary produced somewhere else. The team built a small evaluation set for each AI feature from real, consented examples, and ran it against every model and provider combination the gateway was allowed to use. A route was only enabled for a feature when it passed that feature's evaluation; see evaluation sets that predict production.

The second difficulty was operations. Running identical clusters in two regions doubles the surface area unless they are managed as one. All clusters were built from the same infrastructure code, ran the same serving stack, and were operated from a single multi-cluster view, so engineers could see and act on every region from one place5.

Customer data rules shaped routing as much as capacity did. Some contracts required US-only processing or excluded certain providers. Those rules lived in a per-customer policy the gateway checked on every request, so overflow never sent a restricted customer's data somewhere it should not go. See Kubernetes inference gateway and model routing.

Capacity you cannot move is a dependency you cannot manage. Make moving cheap: same code, same clusters, same evaluations, different place.

What I'd do again, and differently

Again: start with per-request telemetry. It showed that a few features drove most of the cost, which changed the whole capacity plan. Differently: write customer data rules into the gateway before adding the second region; retrofitting them slowed the rollout. FAQ

Common questions

Why would a SaaS company need AI capacity in more than one region?

Because capacity in a single region can be hard to expand when demand outruns supply, and new data centres can be delayed. Serving from several regions and providers keeps AI features available and gives room to negotiate.

Does multi-region serving mean running everything everywhere?

No. In this design, a primary region carries most traffic, a secondary region and managed APIs absorb overflow and failures, and routing decides per request based on capacity, latency and data rules.

How do you keep costs under control across providers?

Record model, provider, tokens and customer on every request, and report cost per feature and per customer. That shows where capacity is worth reserving and where overflow pricing is acceptable.
