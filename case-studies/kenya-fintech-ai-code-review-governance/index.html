Faster, not looser: adopting AI coding agents and automated review at a Kenyan fintech scale-up

A Nairobi fintech scale-up processing mobile money and card payments wanted the speed AI coding tools promised. Engineers were already using them unofficially. Review queues were the bottleneck, and new tools offered agents that review, fix and even approve pull requests. The goal was to adopt them deliberately: more throughput on routine work, tighter control on the code that moves money.

The situation

A Nairobi-based fintech scale-up built payment and lending products on top of mobile money and card rails. Its engineering team had grown quickly, and code review had become the bottleneck: senior engineers spent much of their week reviewing, and simple changes waited days. Engineers were already using AI coding assistants on their own accounts, with no agreed rules on what code or data could be shared with them.

Leadership wanted the productivity, but the products moved customers' money and handled personal data, and bank and mobile money partners expected evidence of a controlled development process. Unreviewed or poorly reviewed changes to payments code were the risk nobody could accept.

Why now. In November 2026 Anthropic launched Claude Ship, a set of agents for GitHub pull requests: code review, an agent that fixes failing checks and conflicts, and an approvals agent that can approve routine changes when a policy file in the repository allows it1. Coverage noted Anthropic's warning that it may miss bugs or security issues2. Tools that can approve code changed the question from "should we use AI to write code?" to "who is allowed to say yes?".

What had to be true

  • One policy for AI tools: which tools, which repositories, what data may be shared.
  • Review effort matched to risk: humans on code that moves money, agents on routine change.
  • Approval rules in the repository, versioned and reviewed like code.
  • A complete trail for every merge: reviewer, approver, checks, policy.
  • Evidence, not belief: delivery and stability measured before and after.

The hard part: deciding who may say yes

The team's first instinct was to argue about whether AI review was good enough. The more useful question was where any reviewer's approval should be sufficient. The answer was a risk tier for every path in the main repositories: payments and ledger code, identity and access, personal data handling and infrastructure were high risk; internal tools, documentation, copy and test-only changes were routine.

Code ownership made the tiers enforceable. GitHub's code owners feature assigns owners to paths, and repository rules can require their review before merging3, with rulesets applying required reviews and status checks consistently across branches4. High-risk paths named human owners; routine paths allowed an agent approval when the approval policy file permitted it, and that policy file was itself owned by the engineering leadership group.

The approval policy file is the most important file in the repository. Whoever can edit it decides what agents may merge, so it needs the strictest owners of all.

The rollout followed the team's existing AI coding policy work, set out in AI coding policy for engineering teams, and agent credentials followed the lessons in coding agents and secrets and the agent-framework compromise: agents ran with scoped tokens and never with deployment credentials.

What I'd do again, and differently

Again: start with risk tiers and ownership; once those existed, every tool decision became easier, and it improved human review too. Differently: involve partner banks' and mobile money providers' assurance teams earlier. They cared less about which AI tool was used than about whether approvals on payment code were traceable, and showing them the audit trail early would have saved a round of questions. DORA's research on software delivery performance gave a shared vocabulary for measuring the change5; see DORA metrics for AI-assisted engineering.

FAQ

Common questions

Should AI agents be allowed to approve code?

Only for changes that are low risk by definition, such as documentation, dependency patches with passing tests or copy changes, and only where a policy file states this explicitly. Code that moves money, handles identity or touches personal data should always need a human owner's approval.

How do you stop AI review becoming a rubber stamp?

Keep humans accountable for high-risk paths through code ownership rules, compare agent findings with human reviews during a trial period, and measure change failure rate and recovery time alongside throughput.

What evidence do auditors and partners need?

For each merge: who or what reviewed it, who approved it, which checks ran and which policy allowed it. Repository rules, code owners and exported audit logs together provide that trail.
