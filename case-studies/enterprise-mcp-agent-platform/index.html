From MCP servers on laptops to a governed enterprise agent platform

Engineers had connected assistants to dozens of MCP servers, some internal, some from the internet, most with broad tokens. Security wanted to stop it; product teams wanted more of it. The goal was a platform that made the approved path the easiest one.

The situation

An organisation had embraced AI assistants faster than it had governed them. Developers connected IDE assistants to MCP servers for the code host, the ticketing system and the data warehouse. Some servers were built internally in an afternoon; others were installed from public repositories. Many used personal access tokens with wide permissions, stored in local configuration files. Nobody could say which servers were in use, who had approved them, or what they had done.

Security's first instinct was to block MCP outright. Leadership's instinct was the opposite: agents were becoming central to engineering and operations, and a ban would simply push usage further out of sight.

What had to be true

  • One place to find approved servers, discoverable by the clients people already use.
  • No long-lived shared tokens. Access flows through the identity provider, per user, with the narrowest scopes that work.
  • Every tool call is attributable to a person, an agent, a server and a version.
  • Writes and destructive actions need explicit, visible consent.
  • Publishing a new internal server is easy if it follows the standard; exceptions are rare and visible.

Architecture

The design followed the ecosystem's own shape: the official MCP Registry is intended as an upstream that organisations build private subregistries on, adding internal servers that should never appear publicly3. The approach is described in more depth in running an enterprise MCP registry.

The data flow, end to end

Step five matters most. The MCP security guidance names token passthrough, where a server forwards a token it received from the client to a downstream API, as an anti-pattern that breaks OAuth security boundaries, and the authorisation specification forbids it12. Every server on the platform validates that tokens were issued for it, and calls downstream systems with its own, separately scoped credentials.

The hard part: scopes people would actually accept

The technical controls were well understood. The difficult part was scope design. The MCP guidance warns that over-broad scopes granted up front expand the blast radius of a stolen token, make revocation disruptive and create consent dialogs that users abandon; it recommends a progressive, least-privilege model starting with a minimal read-only set1. In practice that meant:

  • A small, named set of scopes per server, starting with read-only discovery.
  • Write and admin scopes requested only when a user first invokes a tool that needs them.
  • Central control through the identity provider using the authorisation extensions, so administrators can grant and revoke access in one place4.
  • Metrics on which scopes are requested and used, so creep is visible.

Least privilege only works if the least-privilege path is also the least-friction path. Otherwise people find a personal token and work around it.

What I'd do again, and differently

Again: start with an inventory and make the approved path faster than the unapproved one before enforcing anything. Differently: publish the server template and its CI checks in the first phase. Teams wanted to build compliant servers early, and every week without a template produced another one-off that later needed migrating.

FAQ

Common questions

Why not just let teams install any MCP server?

MCP servers can read data and take actions with the user's access. Unreviewed servers, broad tokens and no audit trail turn a productivity tool into an unmanaged integration layer. A registry and gateway keep the convenience while adding control.

What is token passthrough and why is it forbidden?

It is when an MCP server accepts a token not issued for it and forwards it to a downstream API. The MCP security guidance describes it as an anti-pattern that breaks OAuth security boundaries, and the authorisation specification forbids it.

Does a private registry replace security review?

No. The registry is where approved servers are listed and discovered. Review, version pinning and policy decide what gets listed; the registry makes the decision visible and enforceable.
