Putting FHIR prior authorisation APIs in front of a payer's legacy claims systems

Prior authorisation ran on fax, phone and portals, and a federal rule had set dates for API-based exchange. The goal was standards-based FHIR APIs that providers could call, wrapped around claims and utilisation management systems that could not be replaced in time.

The situation

A regional health payer handled prior authorisation the way much of the industry still does: faxes, phone calls and a provider portal, feeding a utilisation management system that sat beside the core claims platform. Providers waited, reviewers re-keyed information, and nobody could easily answer how long decisions took or why requests were pended.

The CMS Interoperability and Prior Authorization Final Rule (CMS-0057-F) changed the timetable. It requires impacted payers to implement a prior authorisation API, with API compliance dates from January 2027, and to publicly report prior authorisation metrics1. Replacing the claims and utilisation management systems in that window was not realistic, so the question became how to put a standards-based front door on them.

What had to be true

  • Standards, not a bespoke API, so provider EHR vendors could integrate once.
  • No rip-and-replace: the existing systems remain the systems of record.
  • Every decision traceable, with a reason a provider could act on.
  • Humans for clinical judgement: automation handles completeness and clear-cut rules; reviewers handle the rest.
  • Metrics by construction, not by quarterly spreadsheet.

Architecture

The design followed the three HL7 Da Vinci guides that work together for prior authorisation: Coverage Requirements Discovery, Documentation Templates and Rules, and Prior Authorization Support.

CRD uses CDS Hooks so the payer can return coverage requirements inside the provider's ordering workflow2. DTR lets payer documentation rules run in the provider context so the required information is gathered up front3. PAS carries the request as a bundle built around a Claim resource, aligned to the X12 278 transaction, and is designed to be used together with CRD and DTR4.

The data flow, end to end

Status inquiries used the same decision record, so a provider checking on a pended request saw exactly what a reviewer saw, and the answer never depended on which internal system happened to hold the case.

A deeper walkthrough of the rule and the APIs is in CMS-0057 prior authorisation APIs.

The hard part: translating policy into rules people trust

The FHIR plumbing was well specified. Medical policy was not. Coverage criteria lived in documents written for human reviewers, and turning them into DTR questionnaires and rules required:

  • A policy backlog ranked by request volume, so the most common services were automated first.
  • Clinical owners for every rule, with versioning so a decision could be traced to the policy text in force at the time.
  • A firm boundary: rules could approve or route to review, but a denial on clinical grounds always went through a reviewer.
  • Specific, actionable reasons in every pended or denied response, rather than generic codes.

An API that returns "pended" faster is not an improvement. The value is in returning the right question to the provider at the moment they can still answer it.

What I'd do again, and differently

Again: start with the decision record and event stream, because everything else (reporting, audit, provider status checks) hangs off it. Differently: bring provider-side EHR partners into testing earlier. Real Claim bundles from real ordering workflows surface mapping gaps that synthetic tests never do.

FAQ

Common questions

What are CRD, DTR and PAS?

They are HL7 Da Vinci implementation guides. CRD tells the provider at the point of care whether prior authorisation or documentation is needed, DTR gathers the documentation the payer requires, and PAS submits the request and returns the decision.

Do we need to replace our claims system to meet CMS-0057-F?

Usually not. The APIs can sit in front of existing claims and utilisation management systems, translating FHIR requests into internal work items and decisions back into FHIR responses.

Why build metrics from events?

The rule requires prior authorisation metrics to be reported publicly. Deriving them from the same events that drive operations means the published numbers match what actually happened.
