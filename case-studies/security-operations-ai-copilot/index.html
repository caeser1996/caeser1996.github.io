An AI copilot for the security operations centre that analysts trust

A security operations team faced more alerts than analysts, from tools that each spoke their own data format. Leadership wanted AI to help. Analysts wanted it not to invent things or take actions on its own. The goal was a copilot that speeds up triage and investigation while every response stays a human decision.

The situation

A financial services group ran a security operations centre that took alerts from endpoint protection, identity providers, cloud platforms, email security and network tools. Each tool had its own data format and console. Analysts spent much of their time gathering context: which user, which host, what else happened nearby, has this been seen before. Experienced analysts carried that knowledge in their heads; newer ones escalated more than they needed to.

Leadership wanted to apply AI. The security team's concerns were specific: an assistant that invents findings, one that attackers can manipulate through the very logs it reads, and anything that acts on production systems without a person deciding.

What had to be true

  • Every statement cited to the events, alerts or runbooks it came from.
  • Read-only by default: the copilot investigates; it does not change systems.
  • Human approval for every response action, with the action and its reason logged.
  • Consistent data across sources, so the same question gives the same kind of answer.
  • Aligned with the incident response process the organisation already followed and was audited against.

Architecture

The data flow, end to end

Normalisation made the rest possible. OCSF is an open, vendor-agnostic schema for security events, with a framework of data types, an attribute dictionary and a taxonomy2, and it moved under Linux Foundation governance in 20243. MITRE ATT&CK supplied a shared vocabulary for adversary behaviour, so summaries described detections in terms analysts already used4.

The hard part: an assistant that reads attacker-controlled text

Most AI copilots read trusted documents. A security copilot reads email subjects, file names, command lines and web requests, many written by attackers. Prompt injection, listed in the OWASP Top 10 for LLM applications5, is not a theoretical risk here. The design assumed it would be attempted:

  • All event content treated as untrusted data, clearly separated from instructions in every prompt.
  • Tools read-only by default, with narrow scopes; no tool able to change a system directly.
  • Action proposals limited to steps from approved runbooks, and every proposal approved by an analyst.
  • Generated queries shown to the analyst, so the reasoning can be checked rather than trusted.
  • An evaluation set of past incidents, including deliberately manipulated log content, run before each change.

In a SOC, the AI's input is partly written by the adversary. Design as if every log line is trying to give your copilot orders.

The general controls are covered in prompt injection defence for agents and evaluating AI agents.

How it ran

Key decisions and trade-offs

Incident records and handoffs were aligned with NIST SP 800-61 Revision 3, which organises incident response recommendations around the Cybersecurity Framework 2.0 functions1, so the copilot fitted the process auditors already expected. Lessons from incidents fed the approach in AI incident postmortems.

What I'd do again, and differently

Again: normalise data and build the evaluation set from real incidents before writing prompts. Differently: start runbook clean-up earlier. Many proposals were only as good as the runbooks behind them, and some runbooks were out of date.

FAQ

Common questions

Should AI take automated response actions in a SOC?

Only for well-understood, low-risk actions with clear rollback, and even then with logging and review. In this design the copilot proposes actions such as isolating a host or disabling an account, and an analyst approves before a playbook runs.

Why normalise security data before adding AI?

Because an assistant reasoning over a dozen vendor formats will make mistakes a consistent schema avoids. OCSF provides a vendor-agnostic schema for security events, so queries, correlations and summaries work the same way across sources.

How do you stop attackers manipulating a SOC copilot?

Treat everything in alerts and logs as untrusted data, never as instructions. Attackers control content in emails, file names and command lines, so prompt injection is a real risk; tools are read-only by default and any action needs human approval.
