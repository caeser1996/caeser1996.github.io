Every key has an owner: machine and AI agent identity for a South African fintech

A South African investment and payments platform had tightened staff logins years ago. The credentials its software used were another matter: cloud keys in CI, database passwords in configuration, partner API keys shared between services, and now AI agents with their own tool access. After an attack elsewhere showed how quickly automated attackers turn one foothold into every reachable token, the company set out to know, own, shorten and be able to revoke every machine credential it had.

The situation

A South African platform offered investment accounts and payments to retail customers and small businesses. Staff identity was in good shape: single sign-on, multi-factor authentication and quarterly access reviews. Software identity was not. Pipelines deployed with long-lived cloud access keys. Services read database passwords from configuration files. Partner API keys were shared between several services, and nobody was sure which. Over the past year, teams had added AI agents: a support assistant that looked up account status, and internal agents that triaged alerts and drafted reconciliation reports, each with its own set of keys.

As a financial institution in scope of Joint Standard 2 of 2024, issued by the FSCA and the Prudential Authority and effective from 1 June 2025, the company had to maintain cybersecurity and cyber resilience controls, including identity and access management34. A security compromise involving personal information would also trigger notification duties under POPIA. The company's access controls were written around people; its regulator would not see the distinction as an excuse.

Why now. In late October, Chainalysis disclosed an intrusion by an actor using "offensive agentic techniques"2. On 6 November it said the attack had exposed password hashes and live tokens for all users, and it took key products offline1. The lesson for the board was simple: automated attackers find and use every credential they can reach, quickly. Industry research suggested the company was not unusual: a 2026 identity survey reported that only a small minority of organisations automate the lifecycle of machine identities5.

What had to be true

  • Known: every machine and agent credential in one inventory.
  • Owned: each with a named team and a purpose.
  • Short-lived: static keys replaced by credentials that expire in minutes or hours wherever possible.
  • Narrow: each identity allowed only what its job needs.
  • Revocable: all machine credentials can be rotated or revoked quickly, in a tested way.
  • Visible: every action attributable to a specific identity, and unusual use detected.

Architecture

Pipelines stopped storing cloud keys and instead exchanged a signed identity token from the CI system for short-lived cloud credentials. Services on Kubernetes used their service account identities to obtain credentials from the cloud and the secrets manager, which issued database users that expired after a few hours. Kubernetes itself follows the same principle for image pulls, where credential provider plugins fetch registry credentials on demand instead of storing them6. Partner API keys that could not be made short-lived were split so each service had its own, stored only in the secrets manager and rotated on a schedule.

The hard part: agents, delegation and revoking without an outage

Agents acting for customers. The support assistant needed to look up a specific customer's account, but must never be able to look up any account. The token broker issued it a token only after the customer had authenticated in the conversation, scoped to that customer, read-only and expiring with the session. Internal agents had their own identities and could only call tools on an approved list. Every action was logged against both the agent and, where relevant, the person it acted for. See agentic infrastructure.

Revoking everything, safely. The scenario the board cared about was "assume every machine credential is compromised". The first tabletop exercise showed that revoking everything at once would take the platform down, because some services could not obtain new credentials without a restart and a few partner keys had no rotation process at all. Fixing that became its own workstream: services that refresh credentials automatically, a documented rotation for each partner key, and a staged revoke-all runbook rehearsed in a test environment.

If you cannot revoke a credential without breaking production, you do not control it. Make rotation routine before you need it in an emergency.

What I'd do again, and differently

Again: start with the inventory and owners. It found credentials nobody remembered creating, and it made every later decision concrete. Differently: run the revoke-all tabletop in the first month; it exposed the services that could not refresh credentials, which shaped the whole plan. FAQ

Common questions

What is a machine or non-human identity?

Any identity used by software rather than a person: cloud access keys, service accounts, API keys, database credentials, CI tokens and, increasingly, AI agents. They often outnumber human users and are harder to track.

Why do short-lived credentials matter after an agentic attack?

Automated attackers move quickly from first access to every credential they can reach. Credentials that expire in minutes or hours limit what a stolen token can do and how long it stays useful.

How should AI agents be given access to systems?

Give each agent its own identity, issue short-lived tokens scoped to the task through a broker, act on a user's behalf only with explicit delegation, and log every action against both the agent and the user.
