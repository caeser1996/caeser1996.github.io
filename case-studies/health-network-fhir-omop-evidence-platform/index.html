Turning a hospital network's EHR data into a governed real-world evidence platform

Several hospitals, several EHR configurations, and a research team waiting months for every dataset. The goal was one standardised, quality-checked research platform on OMOP, fed from FHIR, that could answer questions locally and join federated studies without moving patient data.

The situation

A hospital network wanted to use its clinical data for research, quality improvement and, eventually, AI. In practice every question became a bespoke extract: a request, a queue, a data engineer writing site-specific SQL against each EHR's reporting database, and weeks of reconciliation when the sites disagreed. The same diagnosis was coded differently between sites, lab units varied, and nobody could say how complete the data was.

The network had already invested in FHIR APIs for interoperability. The question was whether those APIs could become the feed for a research platform, rather than building yet another set of point-to-point extracts.

What had to be true

  • One model for analysis, so a cohort defined once runs everywhere.
  • Standard vocabularies, so "type 2 diabetes" means the same concept set at every site.
  • Measured quality, visible to researchers before they trust a result.
  • Privacy by architecture: identifiable data stays inside each site's boundary, and collaboration happens by sharing code and aggregates.
  • Something the internal team could run after hand-off, without a consultancy on retainer.

Architecture

The design used FHIR for extraction and OMOP CDM v5.4 for analysis, following the direction of the HL7 FHIR-to-OMOP implementation guide, developed by the Vulcan accelerator with the OHDSI community1.

The data flow, end to end

Bulk export was chosen over per-patient API calls because it's designed for population-level extraction, returning newline-delimited JSON files asynchronously2. The detailed pipeline patterns are in FHIR bulk data export pipelines and FHIR to OMOP architecture.

The hard part: meaning, not pipes

The pipeline engineering took less time than agreeing what the data meant. OMOP's standardised vocabularies map source codes to standard concepts in defined domains, which is what makes cross-site analysis possible5. Getting there required:

  • A mapping backlog ranked by how often each unmapped local code appeared, so effort went where the data was.
  • Clinician review for ambiguous mappings, recorded with reasons, rather than an engineer's best guess.
  • Unit normalisation rules for laboratory measurements, agreed with lab leads.
  • A policy for what to do with codes that can't be mapped: keep the source value, flag the concept as unmapped, and report the rate.

More on this in clinical terminologies and OMOP vocabularies.

Quality as a release gate

OHDSI's Data Quality Dashboard runs a large library of checks across conformance, completeness and plausibility4. The key decision was to treat a subset as blocking: if they fail, the new version doesn't publish and researchers keep using the previous one. The rest are published alongside the data, so researchers can judge fitness for their question. See OMOP data quality checks.

Researchers trust a platform that tells them what is wrong with it. Published quality results build more confidence than any feature list.

How a federated study runs

This is the OHDSI network model described in The Book of OHDSI3, and it is what let the network collaborate without centralising identifiable records. More in federated health analytics.

What I'd do again, and differently

Again: start from the research questions, not the tables, and make quality visible from day one. Differently: bring the vocabulary and clinical review effort forward. It's always the critical path, and it's the part that can't be bought.

FAQ

Common questions

Why convert FHIR data to OMOP?

FHIR is designed for exchanging data between systems; OMOP is designed for analysing it consistently across institutions. Converting FHIR to OMOP lets the same analysis code, cohort definitions and quality checks run at every site.

How long does an OMOP implementation take?

It depends on the number of source systems, how well coded the data is, and governance. The vocabulary mapping and data quality work usually take longer than the pipeline engineering, so plan them as first-class workstreams.

Do sites need to share patient data to collaborate?

No. In the OHDSI federated model, each site keeps its data and runs shared analysis code locally, sharing only aggregate results.
