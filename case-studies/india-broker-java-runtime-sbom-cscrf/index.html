A query, not a hunt: building a live software inventory for an Indian stockbroker after Java4Shell

An Indian stockbroker ran its trading, identity and back-office systems on Java, some built in-house and some bought. When Java4Shell was disclosed, nobody could say quickly where every Java runtime was or which version it ran. The SBOMs produced for SEBI's cyber framework listed libraries, not runtimes. The goal was an inventory that answers that question in minutes, and a patch path that rebuilds rather than repairs.

The situation

A mid-sized Indian stockbroker ran most of its estate on Java: an in-house order management service, a customer portal, Keycloak for identity, Jenkins for builds, and several bought products for exchange connectivity, risk and back office, each shipping with its own Java. Some ran in Kubernetes, some on virtual machines, and a few on servers that only the vendor touched.

Under SEBI's Cybersecurity and Cyber Resilience Framework, the firm already produced software bills of materials for software supporting core operations, as regulated entities are expected to, covering in-house, third-party, open-source and SaaS software3. CERT-In's guidelines set out what those SBOMs should contain and have since been extended to other kinds of bill of materials4. On paper, the firm was well placed.

Why now. Java4Shell, a flaw in the Base64 decoder of OpenJDK's runtime, was disclosed in November 2026, with reports that it can enable unauthenticated remote code execution in applications such as Jira, Jenkins and Keycloak2. Updated Java builds arrived on 17 November, with other distributions following on their own schedules1. The first question from the board was simple: where are we exposed? The SBOMs could not answer it, because they listed the libraries each application declared, not the Java runtime underneath.

What had to be true

  • Runtimes in the inventory, not only application libraries: Java, Python, Node and the operating system packages beneath them.
  • Vendor software included, with the components it bundles and the vendor's fix status.
  • Answers by query: which systems run an affected version, who owns them, and are they internet-facing.
  • One patch path: rebuild and redeploy, so what runs matches what was scanned.
  • Regulatory evidence as a by-product, not a separate spreadsheet.

The data flow, end to end

The hard part: making the running estate match the inventory

An inventory is only as good as its link to what is actually running. Two things broke that link. First, Java arrived through many doors: base images from different teams, host packages, and vendor installers each bringing their own runtime. The fix was a small set of golden base images owned by the platform team, so patching Java meant changing one place and rebuilding everything that depended on it. Vendor products were tracked separately, with their bundled runtimes and the vendor's promised fix date recorded against them.

Second, people patched running systems by hand under pressure, which left containers that no longer matched their images. Kubernetes admission control can catch this: the Kubernetes blog describes a validating webhook that tags pods someone has run interactive commands in, and evicts them after a set interval so they are replaced from their declared state5. The team used the same idea, alongside a policy that only admits images built from current golden bases.

An SBOM tells you what you built. A runtime inventory tells you what you are running. For vulnerability response, only the second one matters.

Virtual machines and vendor-managed servers could not use admission control, so host discovery ran on a schedule and any runtime it found that was not in the inventory became a ticket with an owner. The approach builds on the legacy estate modernisation and vulnerability handling case studies, and on supply chain security patterns.

What I'd do again, and differently

Again: treat the inventory as a product with an owner, and make regulatory SBOMs an export from it rather than a parallel effort. Differently: ask vendors for their bundled components and patch commitments at contract renewal, not during an incident. That was the slowest part of the response, and the only part the firm could not engineer its way out of. See vendor admin access as perimeter and the tech news for 19 November.

FAQ

Common questions

Does SEBI require SBOMs?

Yes. SEBI's Cybersecurity and Cyber Resilience Framework expects regulated entities to maintain software bills of materials for software supporting core business operations, covering in-house, third-party, off-the-shelf, open-source and SaaS software.

Why did the existing SBOMs not answer the Java4Shell question?

They were generated from application build files, so they listed libraries the code declared. The Java runtime itself came from base images, host packages or vendor installers, and was not in them.

Why rebuild images instead of patching running containers?

A patched running container no longer matches its image, so the next restart brings the flaw back and nobody can prove what is running. Rebuilding the image keeps what is deployed, what is scanned and what is recorded the same thing.
