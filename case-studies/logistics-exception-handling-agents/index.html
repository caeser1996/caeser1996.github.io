Triaging shipment exceptions with agents that ask before they act

Every delayed shipment produced emails: carriers, customers, warehouses, customs brokers. Staff read, classified and chased each one by hand. The goal was agents that classify exceptions, look up shipment state through governed tools and draft the next action, with a person approving anything that changes the world.

The situation

A logistics operator's customer service and operations teams handled shipment exceptions largely by email. A late container, a failed delivery, a missing customs document or an address query each arrived as free text, often with attachments, sometimes in a long thread. Staff read each message, worked out which shipment it concerned, looked it up in the transport management system (TMS), decided what to do and then did it, across several screens.

The work was repetitive but not trivial. The hard part of each email was usually the same: identify the shipment, understand the exception, gather the facts. The decision itself was often quick once the facts were on one screen.

What had to be true

  • Structured, not chatty: every email becomes a typed exception record, or is routed to a person as unclassifiable.
  • Governed tools: the agent reaches systems only through a defined, permissioned tool layer.
  • Read freely, write with approval: lookups are automatic; anything with side effects needs a person.
  • Inbound email is untrusted and never treated as instructions.
  • Measured and traceable: behaviour evaluated before release, every run inspectable afterwards.

Architecture

The design favoured a defined workflow with agentic steps over an open-ended autonomous agent. Anthropic's guidance on building agents makes the same distinction, recommending the simplest pattern that works and adding autonomy only where it earns its keep1.

The data flow, end to end

Classification and extraction used structured outputs, where the model's response is constrained to a supplied JSON schema5, so downstream steps receive valid records rather than prose. Approval pauses used LangGraph interrupts, which persist graph state while waiting for human input and resume with that input3. More in structured outputs for reliable LLM integration.

The hard part: tools you can trust an agent with

The model was rarely the weak point. The tool layer was where safety lived. The MCP specification describes tools as model-invoked and recommends that a human can always deny a tool invocation2. The design took that literally:

  • Separate read and write servers, with write tools reachable only from the post-approval step of the workflow.
  • Narrow tools: "get shipment milestones" and "request redelivery", not a general API passthrough.
  • Service identity per tool, scoped to the minimum permissions in the TMS.
  • Email as data: inbound text is passed as content to classify, never as instructions, because prompt injection and excessive agency both appear in the OWASP Top 10 for LLM applications4.

The checklist used is in securing MCP servers and prompt injection defence for agents.

Give an agent the narrowest tools that do the job, and put approval in the workflow, not in the prompt.

How it ran

Evaluation followed evaluating AI agents for reliability, scoring classification, shipment matching and proposed actions separately, so a regression could be located rather than just noticed.

What I'd do again, and differently

Again: start read-only, build the labelled set from real emails, and keep write tools behind approval. Differently: invest earlier in shipment matching. Ambiguous references caused more escalations than misclassification did, and better matching would have improved every downstream step.

FAQ

Common questions

Should agents act autonomously on shipments?

Not at first. Read-only lookups can be automated safely; actions that change bookings, notify customers or incur cost should be drafted by the agent and approved by a person until the evaluation evidence supports more autonomy.

Why use MCP for the tool layer?

MCP gives a standard way to describe and expose tools, so the same governed tools can be used by different agents and clients, with permissions and logging in one place.

How do you defend against malicious instructions in inbound emails?

Treat email content as untrusted data, never as instructions; restrict which tools the agent can call from that context, and require approval for any action with side effects.
