Who this is for

You have seen the demos. Perhaps your team built one. It answered the easy questions well and then, in front of a real user, confidently said something wrong. Now legal is nervous, finance wants to know the cost per query and nobody can say whether the next release is better or worse than the last.

I work with leadership teams and engineering leads who are in that position, or who want to avoid it. Typical starting points:

  • An LLM pilot that never made it past the steering committee.
  • A knowledge assistant over internal documents that users stopped trusting.
  • A plan to add agents to a workflow, with no clear view of risk or failure modes.
  • Sensitive data that cannot be sent to a public API, and a mandate to use AI anyway.

The problems I solve

Ungrounded retrieval

Chunking documents into a vector store is a starting point, not an architecture. I combine vector search with structured data and, where relationships matter, a knowledge graph (GraphRAG), so answers cite their sources and respect permissions. The ontology and knowledge graph page explains why the semantic layer matters so much.

No way to tell good from bad

Without evaluations, every change is a guess. I build an evaluation harness from real questions early, and gate releases on it. My RAG to production checklist sets out what I check before anything goes live.

Agents without guardrails

Multi-step agents are powerful and easy to get wrong. I use LangGraph to make state and control flow explicit, expose tools through the Model Context Protocol, and put human checkpoints where a wrong action would be expensive.

Data that cannot leave the building

Private, on-prem inference is now practical. I design AI gateways that classify requests by sensitivity, send regulated data to local open-weight models and route the rest to hosted APIs. More on this in running private LLMs on-prem.

My approach

  1. Start from the decision. What will the system help someone decide or do, and what does a wrong answer cost? That sets the quality bar.
  2. Model the domain. Capture the key entities and relationships so retrieval and agents work from the same meaning as the business.
  3. Build the evaluation set before the features. Real questions, expected answers and edge cases, versioned with the code.
  4. Ship one thin workflow to production. With tracing, cost tracking and guardrails, behind a feature flag.
  5. Expand on evidence. Add sources, tools and agents only when evaluations show they help.
  6. Hand over the platform. Your team owns the pipelines, prompts, evaluations and runbooks.

Common mistakes I see

Choosing the model before the problem

Teams often spend weeks comparing models and almost no time defining what a correct answer looks like. The model choice matters far less than the retrieval, the data and the evaluation set. With those in place, swapping models is a configuration change.

Treating prompts as the product

A clever prompt is easy to copy and hard to maintain. The durable value sits in your data, your domain model and the workflow around the AI: who reviews what, which actions need approval, how errors are caught.

Ignoring cost until the invoice arrives

Token costs scale with usage, context length and retries. I set a cost budget per query from the start, cache what can be cached, and route simple requests to smaller or local models. A system that is accurate but unaffordable at scale is not finished.

Letting agents act without limits

An agent that can send email, change records or call payment APIs needs the same controls as a new employee: narrow permissions, logging and approval for anything irreversible. I design those limits into the graph rather than hoping the prompt holds.

No owner for quality

Someone has to own the evaluation set, review failures each week and decide when a release is good enough. Without that role, quality drifts quietly. I help you define it and train the person who will hold it.

FAQ

Common questions

Why do most LLM pilots fail to reach production?

Usually not because of the model. Retrieval is ungrounded, there is no evaluation set, costs are unknown and nobody owns quality. Fixing those four things gets most pilots moving.

What is GraphRAG and when should I use it?

GraphRAG grounds retrieval in a knowledge graph rather than only in text chunks. It helps when answers depend on relationships between entities, such as customers, contracts and products, and when you need citations and permission-aware access.

Can we run LLMs without sending data to a public API?

Yes. Open-weight models can run on your own GPU hardware or private cloud. I route sensitive workloads to local models and send only non-sensitive work to hosted APIs, behind a gateway that redacts and logs.

Which frameworks do you use?

Mostly LangChain and LangGraph for orchestration, the Model Context Protocol for tool access, and Claude or OpenAI-compatible APIs alongside open-weight models. I choose per problem, not by habit.

How do you measure whether an AI system is good enough?

With an evaluation suite built from real questions and expected answers, tracked on every release, plus tracing in production. Quality, latency and cost per query all get explicit targets.
