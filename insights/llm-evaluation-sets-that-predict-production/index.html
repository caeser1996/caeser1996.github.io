Building LLM evaluation sets that actually predict production

An evaluation set is only useful if a pass means the system will behave in production. Here is the checklist I use to build ones that do, and to use LLM judges without fooling yourself.

A common pattern in AI projects: the evaluation score looks excellent, and production still breaks in ways nobody tested. The score usually isn't wrong. The set is measuring the wrong things: clean questions, easy documents, the happy path.

An evaluation set has one job: a pass should predict that the system will behave well for real users. This is the checklist I work through to make that true.

1. Source the questions from reality

  • Use real traffic, anonymised, wherever you can. Users ask things no one on the team would think of.
  • Weight by importance, not frequency. A rare question about a refund policy or a drug interaction can matter more than a hundred greetings.
  • Include the hard cases on purpose: exact identifiers, ambiguous questions, questions the system should refuse, and questions whose answer is "I don't know".
  • Add every production failure to the set once it is fixed, so it can never quietly come back.

2. Label what "good" means

A reference answer alone is rarely enough. For each example I record the expected answer, the sources it should come from, and the behaviour that matters most, such as citing a source, refusing, or asking a clarifying question. For RAG systems I evaluate retrieval and generation separately, because a right answer from the wrong document is luck, not quality. The RAG production checklist goes deeper on the retrieval side.

3. Choose metrics that match decisions

What you need to knowMetric
Is the right evidence being found?Retrieval recall and precision at k
Is the answer supported by that evidence?Faithfulness or groundedness rate
Is the answer correct and complete?Correctness against labelled answers
Does it refuse when it should?Refusal precision and recall on a held-out set
Can we afford it?Tokens, latency and cost per example

Track cost and latency in the same run. A prompt change that lifts quality by two points and doubles cost is a business decision, not an automatic win.

4. Use LLM judges, but calibrate them

Grading thousands of answers by hand doesn't scale, so most teams use a strong model as a judge. The research supports this with caveats. Zheng and colleagues found strong LLM judges can match human preferences at levels comparable to agreement between humans, and also documented position, verbosity and self-enhancement biases14.

What that means in practice:

  • Calibrate first. Have humans label a sample, run the judge on it, and measure agreement before trusting the judge on the rest.
  • Swap positions when comparing two answers, and count a win only if it holds both ways.
  • Don't reward length. Tell the judge explicitly that longer is not better, and check that it listens.
  • Avoid self-grading where you can: use a different model family as judge from the one being evaluated.
  • Grade against rubrics, with specific criteria, rather than asking "is this good?".

5. Make evaluation a release gate

  1. Version the evaluation set alongside the prompts, retrieval config and model choice.
  2. Run the full suite on every change to any of them.
  3. Set thresholds per metric, including a maximum regression on critical subsets.
  4. Block the release automatically if a threshold fails, the same way a failing unit test would.
  5. Record the results with the release, so you can show what was tested and when.

That last point matters beyond engineering. NIST's Generative AI Profile, a companion to its AI Risk Management Framework, emphasises measurement and pre-deployment testing as part of managing generative AI risk2. A versioned, gated evaluation suite is the practical evidence for that.

6. Close the loop with production

Offline evaluation predicts production only if you keep checking the prediction. I sample live traffic, run the same judges and metrics on it, and compare against the offline scores. When they drift apart, the evaluation set needs new examples. Linking evaluation results to production traces, using standard telemetry such as the OpenTelemetry GenAI conventions3, makes that comparison much easier. I cover the tracing side in LLM observability with OpenTelemetry.

FAQ

Common questions

How big should an LLM evaluation set be?

Start with a few hundred real, labelled examples covering your main tasks and known failure modes. Coverage of the cases that matter is more important than size, and the set should grow every time production reveals a new failure.

Can I use an LLM as the judge?

Yes, with care. Research on LLM-as-a-judge found strong models can agree with human preferences at levels comparable to agreement between humans, but also documented biases such as position, verbosity and self-enhancement bias. Calibrate any judge against human labels before trusting it.

How do evaluations relate to AI risk frameworks?

Frameworks such as NIST's Generative AI Profile emphasise measurement and pre-deployment testing. A versioned evaluation suite that gates releases is the practical way to produce that evidence.
