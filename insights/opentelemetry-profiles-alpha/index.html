OpenTelemetry Profiles is in alpha: the fourth signal and what to do about it

Traces tell you which request was slow. Profiles tell you which line of code burned the CPU. In March 2026 OpenTelemetry's Profiles signal reached public alpha, putting continuous profiling on the same open standard as everything else.

Most observability programmes stop at three signals: traces, metrics and logs. They tell you that something is slow or expensive and roughly where. They rarely tell you why at the level of code. That is what profiling does, and until recently every profiling tool used its own agent and format.

On 26 March 2026 the OpenTelemetry Profiling SIG announced that the Profiles signal had entered public alpha1. It is not ready for critical production use. It is ready for teams to start planning around.

What the alpha includes

According to the announcement, there are three parts1:

  • A standard data format. Stacks are deduplicated and common values stored in dictionary tables for efficiency. Samples can carry trace and span IDs for correlation with traces. Data in pprof format can be converted to and from OTLP Profiles with no loss of information.
  • A reference eBPF profiler. Donated by Elastic in 20243, it provides whole-system profiling on Linux without instrumenting applications. In the alpha it runs as an OpenTelemetry Collector receiver, shipped as an official Collector distribution, with additions including .NET 9 and 10 support and initial BEAM support14.
  • Collector integration. A pprof receiver, Kubernetes metadata enrichment and OTTL transformation rules work with profiles, and Collector v0.148.0 or newer supports the signal1.

Two caveats from the project itself: the signal should not be used for critical production workloads at alpha, and production-ready backends had not yet emerged at the time of the announcement1.

Why this matters

Correlation. The ability to link a profile sample to a trace and span is the real prize. A slow span becomes a flame graph of exactly what that request was doing, without switching tools or guessing.

Cost. Profiling across a fleet shows which functions consume the most CPU and memory. That turns cost work from "buy smaller instances" into "fix the three hot paths", which complements the infrastructure levers in Kubernetes FinOps.

Portability. As with traces, a standard format means you can change profiling backends without re-instrumenting. Vendors in the profiling space have been part of the effort5, which suggests support will follow.

Profiling is the observability signal most teams skip, and the one that most often pays for itself. A standard makes it much easier to justify.

What about AI workloads?

For AI platforms, profiling helps in the parts around the model: tokenisation, retrieval, serialisation, preprocessing and orchestration code, which often consume more CPU than teams expect. Combined with the GenAI tracing conventions in LLM observability with OpenTelemetry, it gives a complete picture of where time and money go in a request. GPU-side profiling is a separate problem; check what your chosen tools cover.

How I would pilot it

  1. Pick a non-critical environment such as staging or a performance test cluster, in line with the alpha guidance.
  2. Deploy the eBPF profiler Collector distribution on a few nodes, with Kubernetes metadata enrichment, and check the overhead yourself.
  3. Choose a backend that accepts OTLP Profiles, or use a development tool to explore the data while backends mature.
  4. Answer one real question, such as the top CPU consumers of your most expensive service. A pilot with a concrete finding wins support for wider rollout.
  5. Keep the pipeline in your Collector configuration, so that promoting it to production later is a configuration change, not a new project.

If you already run continuous profiling with a vendor agent, there is no need to rip it out. Ask the vendor about OTLP Profiles support and plan the switch for when the signal reaches beta.

FAQ

Common questions

What is the OpenTelemetry Profiles signal?

A standard way to capture and transport continuous profiling data in OpenTelemetry, alongside traces, metrics and logs. It defines a data format compatible with pprof, a reference eBPF profiler and integration with the OpenTelemetry Collector.

Is OpenTelemetry Profiles production ready?

Not yet. It entered public alpha in March 2026, and the project says it should not be used for critical production workloads. The announcement also noted that production-ready backends had not yet emerged.

Why does profiling matter for cost?

Profiles show which functions consume CPU and memory across a fleet. That makes it possible to find and fix the code paths that drive compute spend, rather than only scaling infrastructure.
