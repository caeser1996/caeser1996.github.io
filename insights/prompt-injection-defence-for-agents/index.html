Prompt injection and AI agents: stop trying to block it, design to contain it

There is no filter that reliably stops prompt injection. The UK's NCSC says as much. The useful question is not how to block it, but how to design agents so that a successful injection can't do much damage.

Many teams still treat prompt injection like SQL injection: find the right filter, sanitise the input, move on. It doesn't work, and the reason matters for how you design agents.

Why filters don't fix it

SQL injection was solved with parameterised queries, which make it structurally impossible for data to be read as code. The UK's National Cyber Security Centre points out that current LLMs have no equivalent: they don't enforce a security boundary between instructions and data inside a prompt. Its conclusion is that prompt injection may never be mitigated the way SQL injection was, and that effort should go into reducing the impact instead1.

OWASP lists prompt injection first among LLM application risks for the same reason4. Detection products help at the margins, but a defence that stops most attacks still fails against a determined attacker.

The lethal trifecta

Simon Willison gave the problem a useful shape. An agent becomes dangerous when it combines three things2:

CapabilityExample
Access to private dataReading the user's email, documents or database
Exposure to untrusted contentReading web pages, inbound emails, uploaded files
Ability to communicate externallySending email, calling APIs, rendering links or images

With all three, a single poisoned input can tell the agent to collect private data and send it somewhere. Remove any one leg and that path closes.

The design rule I use: no single agent gets all three legs without a human approving the dangerous step. Split the work so the agent that reads untrusted content can't reach private data or the outside world.

Separate planning from reading

Research from Google, Google DeepMind and ETH Zurich, the CaMeL paper, shows what this looks like in practice. A privileged model writes a plan from the trusted user request. A quarantined model processes untrusted data but has no tool access. A separate interpreter tracks where each piece of data came from and checks security policies before every tool call, so untrusted content can't change the plan or send data where it isn't allowed3.

The authors are clear it isn't perfect and doesn't cover every attack3. But the principle is the right one: security decisions are made by ordinary code outside the model, using provenance the model can't forge.

A containment checklist

  1. Map each agent against the trifecta. If one has all three legs, split it or add an approval step.
  2. Enforce permissions outside the model. Tool calls go through a gateway that checks the user's rights, the tool's scope and the data's origin. The model's opinion is not an access control.
  3. Treat retrieved content as data. Mark it as untrusted in the context, and never let it change the agent's permissions or goals.
  4. Constrain outputs that leave the system. Allow-list destinations for email and HTTP, and strip links and images from model output that could carry data out.
  5. Require approval for irreversible actions, showing the exact action and data involved.
  6. Log everything, so an incident can be reconstructed. The tracing approach in LLM observability helps here.
  7. Red-team continuously with injection tests in the release pipeline, alongside quality evaluations.

This complements the protocol-level controls in securing MCP servers. MCP security protects the pipes; containment limits what a confused agent can do with them.

What this means for product design

Containment has a cost. Agents that need approval are slower, and splitting capabilities means more engineering. The trade-off is worth discussing explicitly with product owners: an autonomous agent that reads the internet and sends email on your behalf is a different risk class from one that drafts replies for a human to send. Write the choice down as an architecture decision record, including what would change it.

FAQ

Common questions

Can prompt injection be fully prevented?

Not with today's models. The UK NCSC has argued that LLMs don't enforce a boundary between instructions and data within a prompt, so prompt injection may never be mitigated the way SQL injection can. The practical goal is to limit what a successful injection can achieve.

What is the lethal trifecta?

A term coined by Simon Willison for the combination of an agent having access to private data, exposure to untrusted content, and the ability to communicate externally. Together they let an attacker's instructions exfiltrate data.

What does a containment architecture look like?

Separate the model that plans from the model that reads untrusted content, enforce policies on every tool call outside the model, avoid giving any single agent all three trifecta capabilities, and require human approval for sensitive actions.
