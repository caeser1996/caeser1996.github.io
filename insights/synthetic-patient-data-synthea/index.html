Synthetic patient data: where Synthea helps, and where it can mislead you

Every health tech team wants data to build with before they can get access to real patient records. Synthetic data is the obvious answer, and a good one, as long as you know which questions it can't answer.

Health tech projects often stall in the same place: engineering is ready, but data access agreements, ethics approvals and security reviews take months. Synthetic data fills the gap. Used well, it lets a team build and test an entire pipeline before seeing a single real record. Used badly, it produces a model that looks great in testing and fails on contact with a real hospital.

What Synthea is

Synthea is an open-source synthetic patient generator, described in a 2018 JAMIA paper. It simulates patient lifespans using publicly available data, covering common reasons for primary care visits and high-burden chronic conditions in the United States, and outputs records in formats such as HL7 FHIR and C-CDA, free of legal and privacy restrictions1. For FHIR and OMOP pipeline work, it is the default starting point.

The realism gap

Synthetic data is clean in ways real data never is. A 2026 study using Synthea output notes that real EHR records contain transcription errors, inconsistent formatting, missing fields, local coding conventions and data quality issues not present in Synthea data3. An evaluation presented at the OHDSI symposium summarised earlier findings that some Synthea distributions needed external modification to be realistic, and that more validation was needed for chronic disease tracking2. And it is American by design: teams in other countries have had to adapt it to local profiles5.

Synthetic data tells you whether your system works. It cannot tell you whether your model is right.

De-identified data sits in the middle. HHS guidance describes two HIPAA methods: Safe Harbor, removing specified identifiers, and Expert Determination, where a qualified expert concludes the risk of re-identification is very small4. Free-text notes are the hard part; identifiers hide in narrative.

How I use synthetic data in projects

  1. Build the whole pipeline on synthetic data first: ingestion, FHIR to OMOP mapping, APIs and dashboards. Access requests run in parallel.
  2. Inject realistic mess deliberately. Add missing fields, duplicate patients, odd codes and late-arriving data, so the pipeline's error handling is exercised before real data arrives.
  3. Keep developer environments synthetic permanently. Real data in development is one of the commonest sources of PHI exposure, which matters under HIPAA security expectations.
  4. Validate on real data under governance. Run data quality checks and model evaluations in a controlled environment before any claim about performance.
  5. Label results honestly. Any metric computed on synthetic data is marked as such in reports, so nobody mistakes a pipeline test for clinical evidence.

For AI and LLM work

Synthetic records are excellent for testing LLM applications end to end: prompt construction from FHIR resources, retrieval, safety filters and integration, as in ambient AI scribes. They are poor evidence of how a model will handle real notes and real patients. Build your evaluation sets from de-identified or governed real data wherever the claim is about clinical quality.

FAQ

Common questions

What is Synthea?

An open-source synthetic patient generator described in a 2018 JAMIA paper. It simulates patient lifespans using publicly available data and produces records in standard formats including HL7 FHIR and C-CDA, free of privacy restrictions.

Can I train or validate clinical AI on Synthea data?

It is useful for building and testing pipelines, but not for judging clinical performance. Later evaluations note that synthetic records lack the errors, missing fields and local conventions of real EHR data, and that some distributions need modification to be realistic.

What are the HIPAA de-identification methods?

HHS guidance describes two methods: Safe Harbor, which removes specified identifiers, and Expert Determination, in which a qualified expert determines that the risk of re-identification is very small.
