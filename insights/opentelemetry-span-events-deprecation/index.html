OpenTelemetry is deprecating the Span Events API: what to change, and when

For years there were two ways to record an event in OpenTelemetry. The project has chosen one: events are logs with names, correlated with traces. Existing data keeps working, but new instrumentation should change direction.

If you have instrumented code with OpenTelemetry, you have probably called Span.AddEvent or Span.RecordException. In March 2026 the project announced it is deprecating that API. New events should be emitted as logs, correlated with the active span through context1.

It sounds like a small API change. For platform teams it touches instrumentation guidelines, dashboards, cost and, increasingly, AI telemetry.

Why the change

OpenTelemetry has offered two ways to emit events correlated with traces: span events via the Tracing API, and log-based events via the Logs API134. The announcement lists the problems with having both: split guidance for library authors, duplicate concepts for operators, and slower evolution because every improvement had to be specified twice1. The community has converged on a simpler model: events are logs with names, emitted via the Logs API and correlated through context, a direction set out in an earlier post on logging12.

What changes and what doesn't

ChangingStaying the same
Span event APIs such as AddEvent and RecordException are deprecated in the tracing specificationExisting span event data remains valid in the OTLP trace model
SDKs make log-based events first-classCorrelation across signals works the same way
Instrumentations and semantic conventions move to log-based events in their next major versionsCompatibility options can still show events on spans

As the authors put it, they are deprecating the API for recording span events, not the ability to see events attached to spans1.

The practical risk isn't broken code. It's a dashboard or alert that quietly stops showing exceptions because they now arrive as logs instead of span events.

What I'd do now

  1. Update instrumentation guidelines. New code emits events and exceptions as log-based events correlated with the current span.
  2. Check the logs pipeline. If logs aren't collected through OpenTelemetry yet, events will have nowhere to go. A Collector gateway, as in Collector deployment patterns, is the natural place to route them.
  3. Audit dashboards and alerts that depend on span events, especially exception counts and error views, and test them after each instrumentation upgrade, as the project recommends1.
  4. Confirm backend support for showing log-based events in trace views, so engineers don't lose context when debugging.
  5. Watch costs. Moving events to the logs pipeline may change how they are priced and retained by your vendor. Model it before the switch.

Why this matters for AI telemetry

AI applications produce a lot of event-like data: prompts, responses, tool calls, guardrail decisions. Treating these as named, structured log events correlated with traces fits the GenAI observability work described in LLM observability with OpenTelemetry. It also makes it easier to apply separate retention, redaction and access rules to sensitive content than when it is embedded in spans.

FAQ

Common questions

Is OpenTelemetry removing span events?

It is deprecating the API for recording them, such as Span.AddEvent and Span.RecordException, in favour of log-based events emitted through the Logs API. Existing span event data remains part of the supported trace model, and compatibility options can still surface events on spans.

Do I need to change my applications now?

Not immediately. The project says operators should not need to change applications or dashboards straight away, but should check after upgrades that events still appear where expected. New code should emit events as logs correlated with the current span.

Why is OpenTelemetry making this change?

Having two overlapping ways to emit events split guidance for instrumentation authors, duplicated concepts for users and slowed improvements, which had to be made in two places.
