FOCUS and AI spend: how to make token costs visible to finance

AI spend arrives as tokens, GPU hours and seat licences, often from vendors that bill nothing like a cloud provider. The FinOps Foundation's FOCUS standard is the best bet for a common format, but it doesn't cover everything yet.

A typical AI cost conversation: finance sees one large invoice from a model provider, another from a GPU cloud, a growing line for AI features in SaaS tools, and a Kubernetes bill that now includes GPU nodes. Engineering can't say which product or customer drove any of it. Without that, AI unit economics are guesswork.

What FOCUS is

FOCUS, the FinOps Open Cost and Usage Specification, is the FinOps Foundation's open standard for billing data. The idea is simple: if every provider publishes cost and usage in the same columns, you can combine cloud, SaaS and AI spend in one dataset without writing a custom parser for each.

The standard has moved quickly. Version 1.3 added split cost allocation and a contract commitments dataset25. The FinOps Foundation reports that its steering committee ratified version 1.4 on 4 June 2026, adding new datasets and columns1, and coverage from FinOps X described additional data integrity tooling3.

Where AI fits, and where it doesn't yet

AI usage can be represented with existing columns: token counts as a consumed quantity and unit, the model and price point as a SKU, and AI services under a service category1. That is enough to put model API spend next to everything else.

It is not yet enough for detailed token economics. Reports around FinOps X 2026 described plans for version 1.5 to break down AI spend by token type and workload4. Until that lands and providers adopt it, input versus output tokens, cached tokens and per-feature attribution mostly have to come from your own telemetry.

The architecture I use

  1. A model gateway for every call, which records model, input and output tokens, latency and the calling team, product, feature and, where relevant, customer.
  2. Tracing with GenAI attributes, as in LLM observability with OpenTelemetry, so cost can be tied to user journeys rather than just API keys.
  3. FOCUS as the finance format. Normalise provider exports to FOCUS, and publish internal usage in compatible columns so finance sees one dataset.
  4. GPU allocation for self-hosted models, using the cluster techniques in Kubernetes FinOps and DRA for GPUs.
  5. Reconciliation each month between gateway totals and invoices. Gaps reveal untracked keys and shadow usage.

The single most useful number is cost per successful outcome: per resolved ticket, per document processed, per qualified answer. Tokens are an input; outcomes are what the business buys.

Decisions this unlocks

  • Model routing. Send simple requests to cheaper models once you can see which features use expensive ones.
  • Build versus buy. Compare API spend with the cost of self-hosting, as in build vs buy for AI, using real usage instead of estimates.
  • Pricing. Set customer pricing for AI features with actual unit costs, not hopes.

FAQ

Common questions

What is FOCUS?

The FinOps Open Cost and Usage Specification, an open standard from the FinOps Foundation for cost and usage billing data, so that data from different cloud, SaaS and other providers can be combined and analysed consistently.

Does FOCUS cover AI token costs?

Partly. Guidance maps AI usage onto existing columns, for example token counts as consumed quantity and unit and the model as a SKU. Commentary in 2026 described token-level economics as largely outside the standard so far, with richer AI breakdowns planned for version 1.5.

How should I allocate AI costs today?

Route model calls through a gateway that tags each call with team, product and feature, record token usage per call, and reconcile it with provider invoices normalised to FOCUS where available.
