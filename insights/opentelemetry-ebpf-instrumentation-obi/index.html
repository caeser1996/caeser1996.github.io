Zero-code observability with OBI: where OpenTelemetry's eBPF instrumentation fits

Instrumenting every service with an SDK is the gold standard, and the reason many estates have no tracing at all. OpenTelemetry eBPF Instrumentation, OBI, offers traces and metrics without touching application code. It changes how fast you can get visibility, though it doesn't replace SDKs entirely.

Many organisations have tracing on the services built in the last few years and nothing on the rest: the legacy Java monolith, the vendor binary, the Go service whose author left. Instrumenting each one with an SDK means code changes, releases and ownership that often doesn't exist. So the gaps stay, and incidents in those gaps take longest to resolve.

What OBI does

OpenTelemetry eBPF Instrumentation uses eBPF to inspect application executables and the operating system's networking layer, capturing trace spans, rate-errors-duration metrics, runtime metrics and service relationships for supported Linux workloads, without modifying application code or configuration1. The documentation lists support for languages including Java, .NET, Go, Python, Ruby, Node.js, C, C++ and Rust, visibility into TLS traffic without decryption, context propagation across services, and configuration-free auto-instrumentation on Kubernetes1.

That last point matters most in practice. On a cluster, you can get a baseline service map and latency metrics for everything in days, not quarters.

Log correlation without touching the app

A recent addition addresses a common incident pain: you have a failing trace, but no way to find the matching log lines because the service never added trace context to its logs. OBI can now add trace and span IDs to logs written to stdout or stderr, because through eBPF it knows which request each thread is serving at the moment of the write3.

The boundaries are stated clearly: it applies to stdout and stderr, only annotates lines written while OBI has active trace context, needs elevated privileges, and on older kernels only some write paths are enriched; the common write path needs Linux 6.0 or later. It also needs a small change in the log pipeline3.

eBPF instrumentation is the fastest way to remove blind spots. SDKs are the way to add meaning. Most mature estates will want both.

Where it's heading in 2026

The OBI SIG's 2026 goals centre on a stable 1.0 release for production readiness, with complete configuration documentation, adoption of OpenTelemetry's declarative configuration and telemetry schemas, and test coverage targets. They also plan to expand protocols to messaging systems such as MQTT, AMQP, NATS and Redis pub/sub, extend database support, instrument cloud service SDKs, broaden .NET support, and strengthen integration with OpenTelemetry SDKs for hybrid instrumentation2.

Check the project's current release status before production rollout4, and pilot in non-critical environments first, in line with the stability approach in OpenTelemetry's stable-by-default push.

How I'd roll it out

  1. Start with the blind spots. Deploy OBI where SDK instrumentation is missing, and compare the service map with what teams believe the architecture is.
  2. Route through your Collector gateway, as in Collector deployment patterns, so sampling, redaction and export are handled centrally.
  3. Review privileges with security. eBPF instrumentation runs with elevated access on nodes; treat it as platform infrastructure with the same controls as other node-level agents, enforced through admission policies.
  4. Check data sensitivity. Capturing protocol data, including from encrypted traffic, can expose sensitive values. Configure what is collected and redact at the gateway.
  5. Add SDKs where business context matters, such as checkout flows, AI calls with GenAI attributes, and regulated workflows.
  6. Watch cardinality and cost, since cluster-wide instrumentation can generate a lot of telemetry quickly.

FAQ

Common questions

What is OBI?

OpenTelemetry eBPF Instrumentation, an auto-instrumentation tool that uses eBPF to inspect application executables and the operating system networking layer, capturing trace spans, RED metrics and service relationships for supported Linux workloads without code or configuration changes.

Does OBI replace OpenTelemetry SDKs?

No. It is a fast way to get baseline traces and metrics everywhere, especially for services that are hard to instrument. SDKs remain the way to add business context, custom spans and attributes. The OBI project is strengthening integration with SDKs to support hybrid approaches.

Can OBI correlate logs with traces?

Yes. OBI can add trace and span IDs to JSON and plain-text logs written to stdout or stderr, without changing the application, provided OBI has active trace context at the time of the write. It needs elevated privileges and, for the common write path, a recent Linux kernel.
