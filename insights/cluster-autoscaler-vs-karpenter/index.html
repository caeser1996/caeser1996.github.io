Cluster Autoscaler or Karpenter: how to choose a Kubernetes node autoscaler

Node autoscaling decides how much you pay for Kubernetes and how fast new work starts. Kubernetes now sponsors two autoscalers with different models: Cluster Autoscaler, which grows and shrinks node groups you define, and Karpenter, which picks and launches nodes to fit the pods waiting. Cloud providers increasingly run Karpenter for you. Here is how they differ, and how I decide.

Two models of node autoscaling

The Kubernetes documentation describes node autoscaling as provisioning nodes when pods cannot be scheduled and consolidating them when they are underused, and lists two autoscalers sponsored by SIG Autoscaling: Cluster Autoscaler and Karpenter1. They solve the same problem from opposite ends.

Cluster Autoscaler works with node groups you define in advance: a group of one machine type, another for GPUs, perhaps a Spot group. When pods are pending, it grows the group whose nodes would fit them; when nodes are underused, it shrinks groups. Your choices about machine types are made up front, in the groups.

Karpenter starts from the pods. It reads what pending pods need, chooses machines to fit them within the limits you set in NodePools, launches them directly and manages their whole lifecycle, including replacing and consolidating them later1. Your choices are expressed as constraints rather than fixed groups.

How a scale-up differs

The practical consequence is flexibility. With Cluster Autoscaler, a workload that needs an unusual shape needs a node group that already offers it. With Karpenter, it needs a NodePool whose constraints allow it. That is why Karpenter tends to suit mixed and changing workloads, and why it needs firmer guard rails: a loose NodePool can launch machine types you never tested.

Scale-down is where the real difference is

Scale-up gets the attention, but cost is decided on the way down. Karpenter's disruption controls cover consolidation, which removes or replaces underused nodes with cheaper ones, as well as drift, when a node no longer matches its configuration, and expiry after a set lifetime2. Disruption budgets limit how many nodes can be disrupted at once and can be scheduled, so you can, for example, allow consolidation only outside business hours4.

That power has a cost: pods get moved more often. Workloads without pod disruption budgets, with long start-up times or with local state will feel it. The Headlamp plugin for Karpenter surfaces these scaling and disruption decisions in a UI6, and the view below shows the other side: a node whose disruption was blocked, which is what you want for a protected workload and what you need to notice when it stops consolidation entirely.

Managed options change the question

You may not have to run either yourself. AKS node auto-provisioning provisions and manages virtual machines in response to pending pods using Karpenter, configured through NodePools and AKS-specific node classes3. EKS Auto Mode manages compute for you and replaces nodes after a maximum lifetime of 21 days, which you can shorten5.

Managed versions remove the work of running the autoscaler, but they also make choices for you: node images, lifetimes and which settings you can change. Read the limitations pages before committing, especially if you need particular operating systems, network modes or access to nodes.

How I decide

If your workloads cannot tolerate being moved, Karpenter's main advantage turns into a source of incidents. Fix disruption tolerance first, then change autoscaler.

For AI workloads, I often run both patterns: Karpenter for general and bursty services, and pinned, separately managed GPU capacity where warm nodes and scarce accelerators matter more than consolidation. FAQ

Common questions

What is the main difference between Cluster Autoscaler and Karpenter?

Cluster Autoscaler changes the size of node groups that you define in advance. Karpenter looks at pending pods and launches nodes chosen to fit them, within limits you set in NodePools, and manages their lifecycle including consolidation and replacement.

Do I have to run Karpenter myself?

Not always. AKS offers node auto-provisioning, which runs Karpenter as a managed component, and EKS Auto Mode uses Karpenter-based node management operated by AWS. Self-hosting gives more control in exchange for more operational work.

Is Karpenter always cheaper?

Not automatically. Its consolidation and instance flexibility can reduce waste, but only if workloads tolerate being moved, disruption budgets are set sensibly and instance choices are constrained to types you have tested.
