RDF 1.2 explained: how triple terms let knowledge graphs describe their own statements

Enterprise knowledge graphs constantly need to say things about facts: where a fact came from, when it was true, how confident a model was when it extracted it. RDF has always made that awkward. RDF 1.2 makes it a first-class feature, and narrows one of the big gaps with property graphs.

Most real knowledge graph questions are not just "is this true?" but "according to whom, since when, and how sure are we?". A supplier relationship came from a contract system; a diagnosis came from a coded record; a link between two companies was extracted by a language model with some confidence. In classic RDF, attaching that context to a single fact meant reification patterns that were verbose, inconsistent between teams and awkward to query.

What RDF 1.2 adds

RDF 1.2 introduces triple terms: an RDF triple that can itself appear as a term inside another triple1. To say something about a statement, you use a reifying triple, whose predicate is rdf:reifies and whose object is the triple term; the reifier then carries whatever metadata you need1. This standardises ideas first explored in the RDF-star community work4.

In Turtle 1.2's annotation syntax, a fact and its metadata can be written together, along these lines:

:acme :supplies :globex {| :source :contractSystem ;
                           :since "2024-03-01"^^xsd:date ;
                           :confidence 0.92 |} .

The base fact remains an ordinary triple that existing queries can use, while the annotation hangs off a reifier that refers to it.

The RDF 1.2 Concepts specification reached Candidate Recommendation on 7 April 20262, part of a wider set of RDF 1.2 and SPARQL 1.2 specifications from the working group. SPARQL 1.2 adds the matching query support3. Check the current W3C status before committing production systems to it.

Why it matters for enterprise graphs

NeedBefore RDF 1.2With RDF 1.2
Provenance per factNamed graphs or custom reification patternsStandard reifier with source metadata
Time validityExtra intermediate nodesAnnotations on the statement itself
AI-extracted facts with confidenceSeparate staging graphsConfidence and model version on each fact
Interchange between toolsVendor-specific RDF-star variantsOne standard model and syntax

The AI case is the most pressing. When a model extracts relationships from documents for GraphRAG or entity resolution, every new edge should carry where it came from, which model produced it and how confident it was, so curators can review and agents can weigh it.

A fact without provenance is a liability in an enterprise graph. RDF 1.2 makes the responsible way to store facts also the standard way.

RDF 1.2 and property graphs

Property graph databases have always allowed properties on edges, and they now have an international query language standard, ISO/IEC 39075 GQL5. Edge properties were one of the main reasons teams chose property graphs over RDF. RDF 1.2 narrows that gap with statement-level metadata, while RDF keeps its strengths: global identifiers, ontologies and validation with SHACL, and taxonomies in SKOS.

The choice is still about workload and ecosystem, as discussed in ontology vs knowledge graph vs semantic layer. What changes is that "we need properties on relationships" is no longer a reason on its own to leave RDF.

How I'd adopt it

  1. Check tool support. Triple stores, parsers and SHACL engines adopt new specifications at different speeds; test the features you need in your own stack.
  2. Define a provenance vocabulary before modelling: source system, extraction method, model version, confidence, validity period.
  3. Annotate new facts first, especially AI-extracted ones, rather than migrating everything at once.
  4. Keep base triples queryable, so existing applications keep working while new ones use annotations.
  5. Write shapes for annotations, so required provenance is validated, not just encouraged.

FAQ

Common questions

What is new in RDF 1.2?

RDF 1.2 adds triple terms: an RDF triple that can itself be used as a term in another triple. Statements about statements are made through a reifying triple whose predicate is rdf:reifies and whose object is a triple term. This standardises work that began as RDF-star.

Is RDF 1.2 a W3C Recommendation?

RDF 1.2 Concepts reached Candidate Recommendation in April 2026, the stage before Recommendation. Check the W3C technical reports index for its current status before depending on it in production.

Does RDF 1.2 make RDF the same as a property graph?

No, but it closes a practical gap. Property graphs attach properties to edges natively; RDF 1.2 gives RDF a standard way to attach metadata to individual statements. The data models, query languages and tooling still differ.
