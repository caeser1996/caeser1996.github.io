LLM model routing: paying for the big model only when it matters

Sending every request to the most capable model is the simplest design and usually the most expensive. Routing sends easy requests to cheaper models. Done well it cuts cost substantially; done badly it quietly lowers quality.

Look at a month of prompts in almost any AI product and you'll find a long tail of simple requests: reformat this, summarise that, classify this ticket. Then there is a smaller set of hard ones: multi-step reasoning, ambiguous questions, long documents. Paying top-model prices for all of it is like sending every support call to your most senior engineer.

Two approaches

RouterCascade
How it worksPredicts which model should answer, then calls one modelTries a cheaper model first; escalates if the answer isn't judged reliable

LatencyPredictableHigher on escalated requests
Hardest partTraining a router that predicts difficulty wellJudging reliability of an answer

FrugalGPT, from Stanford, is the best-known cascade: it queries models in sequence and stops when a response is judged reliable3. RouteLLM, from the LMSYS and Berkeley team behind Chatbot Arena, trains routers on human preference data to choose between a stronger and a weaker model per request1.

What the research showed

On public benchmarks, the RouteLLM project reported cost reductions of over 85% on MT Bench, 45% on MMLU and 35% on GSM8K compared with using only GPT-4, while achieving 95% of GPT-4's performance2. The spread is the lesson: savings depend heavily on how much of the workload is easy. Conversational traffic had lots of easy requests; maths problems had fewer.

Benchmark savings don't transfer. The only number that matters is the saving on your traffic at a quality level your users accept, measured on your own evaluation set.

How I design routing

  1. Start with rules, not a learned router. Route by task type the product already knows: classification and extraction to a small model, open-ended reasoning to a large one. This captures much of the saving with no model to maintain.
  2. Put routing in the gateway, not in application code, so policies change in one place. The same gateway records cost per call, as in FOCUS and AI spend.
  3. Evaluate every route. Each model on each route needs a passing score on the relevant slice of your evaluation set before it takes traffic.
  4. Add a learned router only when the rules plateau, and train it on your own data: requests labelled with which model's answer was acceptable.
  5. Monitor quality per route: user feedback, escalations and sampled reviews. Routing failures look like a gradual decline in satisfaction, not an outage.
  6. Keep sensitive routes fixed. Requests involving regulated data may be pinned to private models, as in private LLMs on-prem, regardless of cost.

Don't forget the cheaper levers

Routing is one of several cost tools. Prompt caching and shared prefixes, covered in LLM inference serving, shorter outputs and better retrieval that sends fewer tokens can each save as much as routing, with less risk. I usually apply those first, then route.

FAQ

Common questions

What is LLM model routing?

Choosing, per request, which model should answer: for example sending simple queries to a smaller, cheaper model and harder ones to a stronger, more expensive model.

What is the difference between routing and a cascade?

A router makes one decision per request and calls a single model. A cascade, as in FrugalGPT, queries models in sequence and stops when a response is judged reliable, so hard requests can incur several calls.

How much can routing save?

It depends on your traffic. The RouteLLM project reported large cost reductions on public benchmarks while keeping 95% of the stronger model's performance, but savings on your workload must be measured with your own evaluation set.
