Hybrid search for RAG in MongoDB: when to use $rankFusion, and when $scoreFusion

Pure vector search is great at meaning and poor at exact terms like product codes and drug names. Hybrid search fixes that, and MongoDB now does it natively. Here is how I set it up for retrieval-augmented generation.

The most common RAG failure I see is not the model. It is retrieval returning the wrong passages. Ask a vector-only system about "ICD-10 J45.40" or a specific contract clause number, and it will happily return text that is semantically similar and factually useless.

The fix has a name, hybrid search, and MongoDB announced general availability of native support for it this year, through two aggregation stages: $rankFusion and $scoreFusion1. As a MongoDB Community Leader I get asked about this a lot, so here is how I think about it.

Why vector search alone isn't enough

Embeddings capture meaning. That is their strength and their weakness. They are good at "how do I cancel my subscription" matching "terminating your plan". They are poor at exact identifiers, rare names, codes and numbers, where a single character changes the answer.

Full-text search has the opposite profile: precise on terms, blind to paraphrase. Hybrid search runs both and merges the results into a single ranked list2. In domains full of codes, like healthcare, finance and legal, I now treat it as the default rather than an optimisation.

Two ways to merge

StageHow it mergesWhen I use it
$rankFusionBy each document's position in each sub-pipeline, using reciprocal rank fusionThe default. Scores from vector and text search aren't comparable, and rank fusion doesn't need them to be
$scoreFusionBy normalised scores, combined with weightsWhen you have an evaluation set and want finer control over how much each signal counts

Reciprocal rank fusion gives each document a score based on the reciprocal of its rank in each list, offset by a constant, and sums across lists2. A document that ranks well in both lists rises to the top. It is simple, hard to break, and needs almost no tuning, which is why I start there.

What a hybrid query looks like

Each retrieval method is a named sub-pipeline. You can weight them, and the stage combines the results24. In outline:

db.chunks.aggregate([
  { $rankFusion: {
      input: { pipelines: {
        semantic: [
          { $vectorSearch: { index: "chunks_vec", path: "embedding",
                             queryVector: qv, numCandidates: 200, limit: 20 } }
        ],
        lexical: [
          { $search: { index: "chunks_text",
                       text: { query: q, path: ["title", "body"] } } },
          { $limit: 20 }
        ]
      } },
      combination: { weights: { semantic: 1, lexical: 1 } }
  } },
  { $match: { tenant_id: tenantId, acl: { $in: userGroups } } },
  { $limit: 8 }
])

Treat this as a sketch and check the documentation for exact options and version requirements. Two details matter more than the syntax. First, keep candidate counts generous in each sub-pipeline so fusion has something to work with. Second, apply permission filters inside the retrieval stages where your indexes support it, not only after, so users never retrieve what they couldn't open. The final $match above is a belt-and-braces check, not the main control.

Tuning without guessing

Hybrid search makes retrieval better on average. It does not tell you whether it made your retrieval better. That needs an evaluation set.

  1. Build 100 to 300 real questions with the passages that should answer them. Include exact-term questions on purpose.
  2. Measure recall at k for vector-only, text-only and hybrid. You want to see hybrid beat both, especially on the exact-term questions.
  3. Adjust weights only with evidence. If lexical matches dominate in a code-heavy domain, weight them up and re-measure.
  4. Consider a reranker after fusion. MongoDB's documentation describes reordering fused results by relevance as a further step2. It costs latency, so earn it with numbers.

This is the same discipline I describe in the RAG production checklist: no retrieval change ships without an evaluation run.

Data modelling still decides the outcome

Fusion can't rescue badly shaped data. A few modelling choices make the biggest difference in my experience:

  • Chunk by structure, not by character count. Sections, clauses and table rows make better retrieval units than arbitrary windows.
  • Store identifiers as fields as well as text. Codes, SKUs and clause numbers in their own fields can be matched exactly and filtered on.
  • Keep provenance on every chunk. Source document, version, owner and access list travel with the chunk so answers can cite and permissions can be enforced.
  • Link chunks to entities. When chunks reference concepts in a domain model, you can combine hybrid search with graph-style traversal. That is the bridge to the ideas in ontology, knowledge graph and semantic layer.

One database or two?

Running vector search, full-text search and operational data in one place removes a synchronisation problem that bites many RAG systems: the vector store lagging behind the source of truth. MongoDB has been pushing this single-platform approach for a while35. It is not always the right call. At very large scale or with specialised retrieval needs a dedicated engine can still win. For most teams I work with, fewer moving parts beats a marginal relevance gain.

FAQ

Common questions

What is hybrid search?

Hybrid search runs a semantic (vector) query and a lexical (full-text) query and merges the results into one ranked list, so you get documents that match the meaning of a question and documents that contain its exact terms.

What is the difference between $rankFusion and $scoreFusion?

$rankFusion merges results by their positions in each sub-pipeline using reciprocal rank fusion, so raw scores don't need to be comparable. $scoreFusion merges normalised scores with weights, which gives finer control but needs more tuning.

Is MongoDB hybrid search generally available?

MongoDB announced general availability of native hybrid search with $rankFusion and $scoreFusion in mid-2026, after a public preview in 2025. Check the current documentation for version requirements.
